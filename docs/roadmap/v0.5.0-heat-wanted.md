# CdrBounty v0.5.0 — Heat & Wanted System

**Status:** Planned

## Goal

Let normal server activity generate bounty gameplay dynamically through a configurable Heat system, automatic system bounties, wanted tiers, and bounty escalation.

## Heat Engine

Heat is a server-controlled score representing how aggressively a player is attracting bounty attention.

Suggested default conceptual range: `0-100`, but implementation should keep thresholds configurable.

Possible Heat sources:

- Player kills.
- Kill streaks.
- Killing active bounty hunters.
- Escaping high-value hunts.
- Combat logging if integrated with a reliable combat-tag source.
- Breaking configured server laws/objectives through API hooks.

Heat decay may be time-based and configurable per state.

## Wanted Tiers

Default conceptual tiers:

- `CLEAN`
- `SUSPICIOUS`
- `WANTED`
- `DANGEROUS`
- `MOST_WANTED`
- `PUBLIC_ENEMY`

Names, thresholds, formatting, and gameplay effects should be configurable.

## System Bounties

CdrBounty may create system-funded contracts when Heat crosses configured thresholds.

Requirements:

- System issuer identity distinct from normal players.
- Configurable funding model.
- Maximum automatic bounty cap.
- Cooldown between escalations.
- No recursive economy exploits from repeated Heat cycling.
- Full audit trail.

## Dynamic Bounty Escalation

Possible escalation inputs:

- Time survived while wanted.
- Hunters defeated.
- Consecutive contract escapes.
- Heat tier increases.
- Server event multipliers.

Escalation formulas must be bounded and configurable.

## Survival Tracking

Track meaningful survival metrics such as:

- Time continuously wanted.
- Time at Most Wanted/Public Enemy tier.
- Hunters defeated during current wanted run.
- Current and longest survival streak.

Restart must not reset active wanted runs incorrectly.

## Most Wanted Board

The board should support categories such as:

- Highest active bounty.
- Highest Heat.
- Longest current wanted survival.
- Most hunters defeated.

Queries must be cacheable and safe for larger datasets.

## Legendary Bounty

Configurable bounty thresholds may trigger a Legendary state with:

- Broadcast.
- BossBar/actionbar hooks.
- Placeholder changes.
- Special contract icon/formatting.
- Optional bonus objectives.

Legendary status must not change payout rules unless explicitly configured.

## Administrative Controls

Planned concepts:

- `/cdrbounty heat get <player>`
- `/cdrbounty heat set <player> <value>`
- `/cdrbounty heat add <player> <value>`
- `/cdrbounty heat reset <player>`
- `/cdrbounty wanted inspect <player>`

All manual adjustments are audited.

## Permissions

Planned additions:

- `cdrbounty.wanted.view`
- `cdrbounty.wanted.top`
- `cdrbounty.admin.heat`
- `cdrbounty.admin.wanted`
- `cdrbounty.bypass.heat`

## Acceptance Criteria

v0.5.0 is complete when:

- Heat gains/decay match configuration exactly.
- Wanted tiers transition deterministically.
- System bounties are created once per eligible threshold/event.
- Bounty escalation remains bounded by configured caps.
- Restart preserves active wanted state and survival timers.
- Most Wanted rankings are correct and performant.
- Admin changes are audited.
- Servers can disable automatic Heat while retaining manual bounty functionality.
- Regression tests cover threshold crossing, decay, restart, escalation, and duplicate-event protection.

## Explicitly Out of Scope

- Target scramblers/false trails.
- Alive capture/jail/bail.
- Hunter teams and bounty chains.
- Cross-server Heat synchronization.
