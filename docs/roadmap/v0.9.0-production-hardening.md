# CdrBounty v0.9.0 — Network, Storage & Production Hardening

**Status:** Planned

## Goal

Prepare CdrBounty for long-running production servers and multi-server environments by hardening storage, migrations, recovery, concurrency, performance, and operational tooling.

## Storage Providers

Required providers:

- SQLite for single-server deployments.
- MySQL/MariaDB for larger or shared deployments.

Storage APIs must remain provider-independent at the domain/service layer.

## Connection Pooling

For network databases:

- Use bounded connection pooling.
- Configure pool size/timeouts.
- Detect unavailable database state clearly.
- Avoid blocking the main server thread on normal persistence operations.
- Expose useful diagnostics without leaking credentials.

## Schema Migrations

Introduce explicit versioned migrations.

Requirements:

- Schema version table.
- Ordered migration IDs.
- Upgrade path from every supported pre-v1 schema.
- Failure stops unsafe startup rather than continuing with partial schema.
- Migration logging.
- Backup recommendation before destructive changes.

Downgrades are not guaranteed unless explicitly documented.

## Cross-Server Consistency

For network mode, define authoritative rules for:

- Contract creation.
- Contract acceptance/reservation.
- Claims.
- Hunter/target state.
- Heat updates.
- Season statistics.

Critical operations must prevent two servers from settling the same contract.

Possible techniques include:

- Database transactions.
- Unique constraints.
- Compare-and-set state transitions.
- Row/version locking where appropriate.
- Idempotency keys.

Correctness takes priority over instant propagation.

## Proxy / Network Messaging

Optional messaging may be used for faster cache invalidation or notifications across servers.

The database remains the source of truth unless another architecture is explicitly adopted later.

Network messaging must tolerate:

- Duplicate messages.
- Out-of-order messages.
- Missing messages.
- Server reconnects.

## Idempotent Settlement

Every payout/refund/bail settlement must have a unique operation identity.

Retrying an operation after timeout/restart must produce either:

- The same completed result, or
- A clear pending/manual-recovery state.

It must never generate a second payout.

## Crash & Restart Recovery

On startup, CdrBounty must reconcile transitional states such as:

- `CLAIMING` contract with unknown payout outcome.
- Reserved contract whose reservation expired while offline.
- Capture in progress when one/both players are absent.
- Expired contract not yet processed.
- Pending refund.
- Season rotation interrupted mid-process.

Recovery decisions must be logged and inspectable.

## Caching

Cache only data with defined invalidation strategy.

Likely cache candidates:

- Player profiles.
- Active bounty summaries.
- Hunter rankings.
- Placeholder results.
- Most Wanted board.

Critical settlement checks must not trust stale cache state over authoritative storage.

## Performance Targets

Testing should include realistic simulated data for:

- Thousands of known players.
- Hundreds/thousands of historical contracts.
- Many simultaneous active bounties.
- Multiple hunters tracking targets.
- Leaderboard refreshes.
- Restart/reload scenarios.

No high-frequency listener should perform uncontrolled database queries or expensive graph scans on the main thread.

## Abuse & Race-Condition Regression

Test at minimum:

- Two killers/servers attempt same claim.
- Contract expires while claim begins.
- Admin cancels while claim begins.
- Hunter abandons while target dies.
- Team membership changes during settlement.
- Economy/provider timeout during payout.
- Duplicate proxy message.
- Database reconnect during active transaction.
- Rapid Heat threshold crossing.
- Double bail payment attempt.

## Operational Tooling

Planned admin diagnostics:

- Storage health.
- Migration version.
- Queue/pending operation count.
- Stuck settlement inspection.
- Contract reconciliation.
- Cache stats/invalidation.
- Database latency summary.

Administrative repair commands should require explicit confirmation/permissions and create audit records.

## Backup & Restore Guidance

Document:

- What files/tables contain authoritative state.
- Safe backup procedure.
- Whether live backup is supported per provider.
- Restore steps.
- Required config/secret files not stored in database.

## Acceptance Criteria

v0.9.0 is complete when:

- SQLite and MySQL/MariaDB pass the same core persistence test suite.
- Migrations from all supported earlier schemas pass against test fixtures.
- Cross-server claim race settles exactly once.
- Crash-recovery tests leave no duplicated payouts.
- Main-thread profiling shows no uncontrolled database/I/O paths in hot gameplay listeners.
- Cache invalidation is deterministic in single-server and network mode.
- Startup clearly reports storage/migration failure and refuses unsafe partial operation.
- Operational diagnostics can identify pending/stuck transactions.
- Backup/restore documentation has been validated on a clean test environment.

## Explicitly Out of Scope

- Redis as a mandatory dependency.
- Web administration dashboard.
- Cross-network/global marketplace.
- Automatic database downgrade tooling.
