# CdrBounty v1.0.0 — Production Release

**Status:** Planned

## Goal

Ship the first stable CdrBounty release with documented behavior, stable public interfaces, validated migrations, operational guidance, and a release process suitable for real servers.

## Release Scope

v1.0.0 is not a feature-dump phase. It is the stabilization and release gate for the systems completed in earlier roadmap phases.

Focus areas:

- API/configuration stability.
- Regression closure.
- Migration validation.
- Documentation completeness.
- Performance verification.
- Packaging and release hygiene.

## Stable Public Surface

Before tagging v1.0.0, freeze and document:

- Public Java API packages.
- Public Bukkit events.
- Placeholder identifiers.
- Command names/aliases.
- Permission nodes.
- Configuration keys intended to remain stable.
- Storage migration guarantees.

Breaking changes after v1.0.0 should require an appropriate major-version change unless a security/data-integrity issue makes emergency action necessary.

## Required Documentation

The release must include:

- Installation guide.
- Quick-start guide.
- Full command reference.
- Full permission reference.
- Configuration reference.
- Storage/database setup guide.
- Migration/upgrade guide.
- Integration guide.
- Public API examples.
- Troubleshooting guide.
- Backup/recovery guide.
- Security and anti-abuse notes.
- Changelog.

## Fresh Install Validation

Test at minimum:

- Clean Paper target server.
- No optional integrations.
- Vault + supported economy.
- Default SQLite configuration.
- Default config generation.
- First bounty lifecycle.
- First contract lifecycle.
- Restart and persistence.

The plugin must either operate safely or give an explicit actionable startup error when a required capability is absent.

## Upgrade Validation

Validate supported upgrade paths from prior public builds.

For each supported source version:

- Backup fixture.
- Start new build.
- Run migrations.
- Validate bounty totals.
- Validate escrow totals.
- Validate contracts.
- Validate hunter profiles/statistics.
- Validate Heat/wanted state.
- Validate season data.
- Validate no duplicate settlement records.

## Regression Matrix

Required test areas:

- Economy and escrow.
- Bounty lifecycle.
- Contract lifecycle.
- Condition evaluation.
- Hunter progression.
- Intel/tracking permissions.
- Heat/wanted transitions.
- Capture/jail/bail.
- Counterplay tools.
- Teams/social mechanics.
- Integrations.
- SQLite and MySQL/MariaDB.
- Restart/crash recovery.
- Multi-server claim races where supported.

## Performance Verification

Profile:

- Player death/claim hot path.
- High-frequency movement/tracking logic.
- Placeholder requests.
- Leaderboard refresh.
- Heat updates.
- Contract browser loading.
- Startup migrations.
- Database reconnect behavior.

Release blockers include uncontrolled main-thread I/O or reproducible gameplay-impacting stalls caused by CdrBounty.

## Security / Abuse Review

Review at minimum:

- Permission bypasses.
- Command argument validation.
- Economy duplication.
- Item reward duplication.
- Contract reservation races.
- Same-player/collusion abuse.
- Capture griefing.
- Tracking privacy bypasses.
- Admin command misuse.
- Webhook/log injection where applicable.
- Unsafe serialization/deserialization.

## Release Artifact

Release checklist:

- Version metadata set to `1.0.0`.
- Clean build from source.
- Tests pass.
- Jar inspected for accidental secrets/dev files.
- Dependency/license notices reviewed.
- SHA-256 checksum generated.
- Changelog finalized.
- Git tag created.
- GitHub release notes prepared.
- Documentation references updated from planned to stable where applicable.

## Compatibility Statement

The final README/release notes must clearly state:

- Supported Minecraft/Paper versions.
- Required Java version.
- Required dependencies.
- Optional dependencies/integrations.
- Supported storage backends.
- Known limitations.

Do not claim compatibility that has not been tested.

## Acceptance Criteria

v1.0.0 may be tagged only when:

- No known critical/high-severity data-integrity bug remains.
- No known reproducible reward duplication path remains.
- Fresh-install test passes.
- Supported upgrade tests pass.
- Restart/crash recovery tests pass.
- Core regression suite passes on supported storage providers.
- Public API and configuration documentation matches the build.
- Commands and permissions are fully documented.
- Production backup/recovery guidance exists.
- Release artifact is reproducible and contains no credentials/secrets.
- Changelog and compatibility statement are complete.

## Post-v1 Direction

Potential post-v1 tracks may include:

- Native Bedrock Forms UX.
- Web dashboard/API service.
- Redis-assisted network messaging.
- Richer fraud/risk scoring.
- Cross-network seasons.
- Additional economy/reward providers.
- Advanced event templates.

These should be evaluated only after real v1 production feedback identifies which direction provides the most value.
